# 审查输出格式规范

本文件定义代码审查报告的输出格式，供子 agent 在第五步（生成审查报告）时参考。

**标题要求（最高优先级）**：报告的第一条非空内容**必须**是一级标题 `# 代码审查报告 - {PROJECT_NAME}`（`{PROJECT_NAME}` 取自注入的项目名称）。它必须是报告的第一个有效行；前置任何空行、emoji、引用块，或直接以 `### ⚙️ 审查配置快照` 等 `##`/`###` 标题开头，都会导致飞书云文档显示为 `untitled`。该一级标题是飞书云文档标题的唯一来源（`lark-cli docs +create` 不接受 `--title`），同时也是主 skill 飞书上传的前置校验，子 agent 落盘前必须自行校验该标题行存在。「审查配置快照」等章节紧跟一级标题之后输出。

**语言要求**：整份报告必须使用中文撰写；代码标识符、配置键、类名、方法名、框架名可保留原文。

**核心排列规则**：所有问题严格按 **P0 → P1 → P2 → P3 → 待确认** 优先级排序输出。**不按维度分组**，每条问题通过「所属维度」字段标注其所属审查维度即可。

**证据规则**：每条问题必须给出可追溯证据，禁止只有纯文字结论。证据可以是代码片段、配置片段、依赖坐标、目录结构、调用链、Git diff、测试缺失证明、扫描结果或运行命令输出摘要。代码级问题优先贴代表性代码片段，并用 `// ←` 标注问题行；非代码级问题使用最能支撑结论的证据类型。

## 分批合并报告格式

`core/merge-batch-results.sh` 生成的分批合并报告是确定性脚本报告，不重新启动 agent 重写结论。它必须包含以下章节：

- `审查配置快照`：记录生成时间、审查类型、审查范围、审查模式、语义增强、Run ID、本轮主任务批次、已纳入合并批次、遗留批次和文件覆盖率。
- `审查范围说明`：说明项目名称、覆盖方式、覆盖口径和未纳入范围。
- `大仓库审查执行摘要`：汇总批次状态、覆盖率和去重后的已合并问题数。
- `批次状态总览`：列出所有批次状态、本轮主任务标记、合并处理、文件数、行数、模块和错误信息。错误列为 `[短标签] 原error`：批次为 `failed` / `partial` 且错误文本非空时，按解析出的中断归因统一加固定五选一中文短标签前缀（含 `[未知]`，如 `[上下文耗尽] 上次执行中断，需要整批重跑`）；其余状态与空错误保持原文。`partial`（部分完成）批次的合并处理标注为「部分完成已纳入」（已产出发现进入正式结论，覆盖保守不计）或「部分完成未纳入本轮，遗留」。
- `已纳入批次发现`：只包含已纳入本次合并的 completed / partial 批次结果，并在写入前按内容指纹做确定性去重——指纹 = sha256(文件路径 ␀ 维度标签 ␀ 归一化证据行)，即按文件 × 维度 × 证据代码内容指纹去重；证据行归一与跨文件重归档同口径（trim → 剥 +/- → trim、空行全弃），文件路径按原字节保留（不做相对化/小写化），行号与措辞不入键。仅当块既无 `- 文件：` 行又无闭合围栏证据时才退回旧整块折叠键兜底，两类键命名空间独立绝不互相命中。相同事实的措辞漂移块只保留首个。每个纳入批次的发现清单保留其 `## 覆盖情况` 披露（已审文件 N/M 与逐文件跳过原因）。
- `跨批次去重`：合并重复数大于 0 时输出统计行——「跨批次去重：N 条发现中合并重复 M 条（按文件 × 维度 × 证据代码指纹），保留 K 条」（N=进入去重的输入发现数、M=被合并的重复数、K=保留输出数）；同一口径写入 `summary.json` 的 `dedup` 对象（`input_findings`=N / `merged_duplicates`=M / `output_findings`=K），`dedup.input_findings` 为 0 时整个 `dedup` 对象省略。
- `跨批依赖线索`：汇总已纳入批次中的跨批依赖待复核内容。
- `跨文件重归档`：合并脚本在去重前对纳入批次自动执行跨文件重归档（fail-open）——证据代码在声明文件内只修正行号漂移；声明文件内找不到证据时，仅当证据代码在审查范围内逐行唯一命中另一文件才迁移位置（文件+行号一起动），0 处或多处命中保持原状。覆盖说明输出 `跨文件重归档：修正行号 N 处、迁移发现 K 条` 统计行；跳过时输出跳过原因。
- `覆盖限制与未审查范围`：说明失败、待执行、执行中、结果缺失或未纳入本轮的批次不进入正式问题结论；partial 批次已产出发现纳入结论，但其覆盖按保守口径不计入覆盖率。

分批合并报告只有在全部计划批次都已纳入合并时才能使用完整报告标题；只要存在未纳入合并的计划批次，即使这些批次已经 completed，也必须标记为 `[阶段性]`。存在已纳入合并的 partial 批次时，报告同样保持 `[阶段性]`，等待整批重跑后再升级为完整报告。

### 失败归因枚举

`failure_class` 是批次状态 JSON 的中断归因字段：`failed` 与 `partial` 必填、判不准写 `unknown`，`completed` 不得携带该字段。只允许以下五个枚举值组成的封闭集合，禁止发明其他值；合并脚本按「显式声明恒优先（仅采纳枚举内值）→ 缺失或枚举外时对 `error` 文本做确定性中文关键词回退 → `unknown`」的次序解析——关键词族按序首个命中生效：上下文|context→context_exhausted、工具|轮次|tool→tool_budget_exhausted、中断|截断|truncat→output_truncated、取消|cancel|interrupt|ctrl→cancelled，其余一律 `unknown`（error 为空同样落 `unknown`）。批次状态总览的错误列为 `[短标签] 原error` 格式：`failed` / `partial` 且错误文本非空时统一加 `[短标签]` 前缀（固定五选一，含 `[未知]`），其余状态与空错误保持原文。

`summary.json` 在 `failed_batches` 字段之后新增 `"failed_by_class"` 对象：五个枚举键全部出现且含零计数（本轮零失败时整个对象省略），五键计数之和等于 `failed_batches`。run-manifest 的 failed/partial 条目以解析后的枚举值写入 `failure_class` 字段，字面量不再保留解析前的写法。

| 枚举值 | 中文短标签 | 触发条件 |
|---|---|---|
| context_exhausted | 上下文耗尽 | 上下文/窗口不足以完成整批，可整批重跑、建议拆批缩小范围 |
| tool_budget_exhausted | 工具预算耗尽 | 工具调用轮次/工具预算耗尽，可原样重试 |
| output_truncated | 输出中断 | 报告/发现清单写入中途断掉（部分产出场景多为 partial），可原样重试 |
| cancelled | 已取消 | 用户或宿主主动中断执行，重跑前先人工确认 |
| unknown | 未知 | 无法归入以上任何一类时的兜底值（禁止乱猜） |

注意：`show-batch-status.sh` 的失败归因展示只采信状态文件显式声明的 `failure_class`（封闭枚举内），不做文本回退猜测——这是有意保留的行为，保证展示口径与 merge 解析口径职责分离。

## P0 证据门槛

每条 P0 必须在证据、影响和建议中明确证明：生产路径可达、置信度高、后果达到事故级、没有足以阻断事故的有效防护，并且问题必须阻断发布。任一项无法证明时不得输出为 P0，应按审查模式进入 P1、待确认或更低级别。

## 问题条目通用规则（最高优先级，强制遵守）

所有 P0/P1/P2/P3/待确认 问题**逐条独立成块输出**，每一条都必须有完整的结构化字段，**禁止**用列表/一句话把多条问题压缩成一节。这是报告体量的核心来源——读者看到汇总表说有 N 个问题，正文里就必须有 N 个独立展开的问题条目。

**逐条完整输出（强制）**：

1. **每条问题用三级标题 `###` 开头**，标题格式固定为 `### {问题编号} | [维度名称] {问题一句话标题}`，例如 `### P0-1 | [维度5-安全] 所有接口无认证 + LLM 可执行 Shell 命令导致 RCE`。标题中的「问题一句话标题」必须概括本条问题，不得只写编号。**禁止**用 `**问题编号**：P0-N` 这种加粗字段代替三级标题，也**禁止**把整条问题塌缩成列表项 `- P0-1：xxx`。
2. **每条问题必须包含完整字段**：位置、置信度/所属维度、问题、证据、影响、建议（待确认项为「依据/待确认原因/建议的验证方式」）。**禁止**为了省输出而省略其中任何一段，尤其是禁止把 P1/P2/P3 的问题只写成「位置 + 一句话建议」。
3. **上下文紧张时优先压缩单条内的代码片段长度**（缩短证据代码块、合并同类证据），**绝不允许**压缩问题条目数量。若问题数过多导致单次输出接近上限，应缩短每条的证据代码片段（保留 `// ←` 问题行标注即可），而非删除问题条目或把多条合并成一句。
4. **同级问题之间用 `---` 分隔**，每条之间空一行，保证飞书云文档里每个 `###` 问题标题可点击跳转、独立成段，同时不与 `##` 级别的问题类别章节混在同一层级。
5. **同类聚合**：同类问题多处出现只算一条，位置只列一个代表处并标注同类总数（如 `A.java:45（同类问题共3处）`），不逐个列出所有位置。

## 大仓库审查执行摘要

Maven 大仓库分批审查报告必须额外包含本节。合并阻塞报告、阶段性报告和完整报告都需要展示，区别在标题、批次状态总览和覆盖率说明。

分批审查报告必须包含：
- Run ID
- 审查分支
- 审查模式
- 审查模型
- 语义增强：`jdtls-lsp` 或 `maven-static`
- 语义增强使用情况：当语义增强为 `jdtls-lsp` 时，必须列出实际使用的 definition / references / implementations / call hierarchy 能力、覆盖的关键类/接口/入口点，以及失败或降级说明；当语义增强为 `maven-static` 时，说明使用 Maven 静态依赖与文本检索
- 本轮主任务批次：本轮 `RUN_BATCH_IDS` 数量 / 总批次数
- 批次完成情况：已完成 / 失败 / 部分完成（partial） / 待执行 / 执行中
- 已纳入本次合并批次
- 遗留批次
- 批次状态总览：批次、状态、本轮主任务、合并处理、文件数、行数、模块、错误
- Java 行规模参考
- Java 文件覆盖率
- 未完成批次说明

合并阻塞报告标题必须包含 `[合并阻塞]`。当本轮主任务批次存在 `failed`、结果文件缺失、等待超时或仍未完成批次时，必须生成合并阻塞报告并标明失败/遗留批次，不能静默跳过。

阶段性报告标题必须包含 `[阶段性]`。

完整报告仅在所有批次为 `已完成` 且纳入合并后生成。阶段性报告合并本轮已完成批次的发现，并纳入 partial 批次已产出的发现（标注「部分完成已纳入」，覆盖保守不计）；未纳入本轮或未完成批次不得进入正式问题结论，必须在批次状态总览中列为遗留。
