# 企业级 Security 专项审查框架

**框架版本：Security 1.0**
**适用模式：`security`**
**定位：跨 Java、Python、Frontend/Node 的安全专项共同审查依据**

## 1. 目标与边界

本框架为 Security 专项提供统一的安全语义、取证步骤、分级门槛和输出契约。语言及框架规则只负责把本框架映射到实际实现（例如 Spring Security、Django/DRF、FastAPI、Node middleware）；不得另行定义冲突的安全结论。

本框架执行静态代码、配置、依赖和可见调用链审查。它不把“缺少注解”“变量名可疑”或“框架默认行为”直接当作已证实漏洞；无法从当前仓库闭合的网关、运行配置、策略中心、数据库行级策略或真实数据条件，必须标记为“待确认项”，并给出最小验证方式。

Security 专项必须覆盖全部正式源码边界，并优先审查入口、身份/权限中间件、资源查询与写入、文件/导出、异步/RPC、管理接口、配置和依赖文件。测试、迁移和生成代码只可作为只读上下文，除非语言框架另有正式配置约定。

## 2. 安全模型：从入口到敏感效果

对每个关联审查单元建立一条安全契约。不得以预置类名、方法名、字段名或装饰器词表代替语义判断。

```text
入口 Entry
  → 主体 Subject / 身份来源 Identity
  → 凭据 Credential / 授权证据 Authorization Evidence
  → 动作 Action
  → 资源 Resource / 资源标识 Resource ID
  → 归属关系 Ownership / Tenant / Scope
  → 授权决策点 Decision
  → 防护 Control（拒绝、降权、隔离、限流、幂等等）
  → 敏感效果 Sink（读、写、删除、导出、调用特权能力）
```

每条契约必须回答：

1. 哪个动作受到保护，最终效果是什么？
2. 当前主体从哪里产生，是否可能被客户端输入伪造或替换？
3. 授权证据由谁产生、如何传播、在哪里解释？
4. 资源是否与主体、租户、组织、角色、关系或 scope 绑定？
5. 缺失、未知、异常、未匹配或多个策略都未决定时，最终是拒绝还是放行？
6. 是否存在绕过入口、批量入口、异步入口、缓存入口或下游入口？

主动构造反例：是否存在“未获得明确授权证据 → 仍到达受保护动作”的可达路径？反例成立后再按证据和影响定级。

## 3. 企业级漏洞域

### 3.1 身份与认证

- 认证缺失、认证绕过、匿名路径误放行和安全开关 fail-open。
- JWT、Session、Cookie、刷新令牌、撤销、重放和会话固定。
- 客户端可控 header、query、cookie、localStorage、postMessage 直接成为身份或租户来源。
- 网关认证与下游服务身份不一致，或 RPC、消息、定时任务中丢失身份上下文。

### 3.2 授权与越权（重点）

- **水平越权 / BOLA / IDOR**：同角色主体访问其他主体资源。
- **垂直越权 / BFLA**：低权限主体执行管理员、内部或高风险动作。
- **跨租户/组织/商户/部门访问**：读、写、删除、导出、统计和搜索条件缺少隔离。
- **主体—资源绑定缺失**：只校验登录态，不校验 owner、组织、关系、scope 或数据权限。
- **批量与间接入口绕过**：列表、搜索、批量修改、导出、下载、预览、文件 URL、GraphQL 字段和聚合接口未复用单资源授权。
- **嵌套资源换绑**：只校验子资源 ID，未校验其父资源属于当前主体或租户。
- **质量与权限混淆**：前端按钮、菜单、路由 meta、DTO 字段隐藏不能作为后端授权证据。
- **混淆代理与过度授权**：服务账号、内部 API、工具调用代替用户执行动作时，主体和权限范围未收敛。
- **检查—使用竞态（TOCTOU）**：授权检查与实际读取/写入之间可被替换、重放或并发绕过。

### 3.3 输入、执行与协议注入

- SQL/NoSQL、命令、表达式、模板、LDAP、XPath、反序列化和代码执行注入。
- XSS、开放重定向、HTTP 请求走私或协议解析边界错误。
- 用户输入到查询、渲染、日志、消息、脚本、文件路径或外部调用的完整传播链。

### 3.4 外部资源与文件

- SSRF（协议、域名、IP、重定向和云元数据访问控制）。
- 路径穿越、任意文件读取/下载、上传类型绕过、Zip Slip 和压缩炸弹。
- 不安全反序列化、多态类型白名单缺失和不可信文件解析。

### 3.5 数据、密钥与隐私

- 敏感字段越权返回、批量导出、错误响应和日志间接泄露。
- 密钥、令牌、密码、连接串硬编码或进入客户端 bundle。
- 加密、密钥轮换、脱敏、最小字段和第三方外传边界不成立。
- 弱密码算法、可预测随机数、密钥生命周期缺口以及 TLS/证书校验被关闭。

### 3.6 业务安全与可用性

- 重放、重复提交、幂等键缺失、状态机跳转和并发竞态。
- 验证码、密码重置、账户锁定、资源枚举和频率限制绕过。
- 关键写操作的授权、额度、库存、资产或状态检查与最终提交不一致。
- 对象属性级授权缺失、批量赋值/mass assignment、未限制字段更新。
- 不受限资源消耗、昂贵查询/导出、并发放大和敏感业务流自动化滥用。
- API 资产清单、影子/旧版本接口未纳入同一认证授权策略。
- 第三方 API、Webhook 或不可信响应被直接信任，缺少 schema、来源和权限约束。

### 3.7 日志、告警与异常安全

- 认证失败、越权拒绝、敏感操作和策略变化缺少结构化审计日志或告警。
- 日志泄露凭据/PII，或可被注入换行、伪造操作者与请求关联信息。
- 异常处理、超时、熔断和降级把未知状态转换为成功/放行，或吞掉安全事件。

### 3.8 配置、依赖与 AI 集成

- CORS、CSRF、管理端点、调试、默认账号、错误页、容器用户和安全响应头。
- 依赖版本、构建插件、CI 权限、未锁定 action、供应链脚本和发布凭据。
- LLM 工具调用的主体授权、参数边界、危险能力白名单和 RAG 数据权限过滤。

### 3.9 基线映射

Security 专项以本框架为执行契约，并用 OWASP Top 10:2025、OWASP API Security Top 10:2023 和 OWASP ASVS 5.0.0 做覆盖校验（不替代本框架的证据与分级规则）。若基线条目在本框架尚无对应检查点，报告中必须列为覆盖缺口或待确认项。

## 4. 静态取证流程

按以下顺序执行，避免只在单个 Controller 或路由文件上猜测：

1. 枚举入口：HTTP、RPC、消息、任务、回调、文件 URL、GraphQL、WebSocket 和工具函数。
2. 枚举受保护动作：受限数据读取、关键状态改变、删除、导出、外部特权调用。
3. 追踪身份与授权证据：认证中间件、策略调用、角色/scope、租户上下文和主体传播。
4. 追踪资源绑定：资源 ID 来源、查询条件、owner/tenant/org 过滤、父子资源关系和批量条件。
5. 追踪最终效果：查询返回、数据库写入、文件响应、消息发送、下游 RPC 和工具执行。
6. 逐状态检查：通过、拒绝、缺失、异常、未匹配、超时和多个处理器均未决定时的结果。
7. 检查绕过面：并行入口、缓存、异步任务、内部接口、导出/下载、重试和补偿路径。
8. 反向验证：尝试构造未授权主体到敏感效果的最短路径，并记录阻断点或缺口。

只使用当前代码中已经识别出的实际符号查询 definition、references、实现和下游效果。语义工具不可用时，必须披露已降级为静态检索，不能声称完成了语义查询。

## 5. 证据等级与输出

每条安全结论必须归入以下一种证据状态：

| 状态 | 适用条件 | 输出要求 |
|------|----------|----------|
| 静态已证实 | 当前仓库已闭合入口、主体、资源、授权缺口和敏感效果链 | 可进入正式 P0/P1/P2/P3 定级 |
| 待确认项 | 依赖运行配置、网关、策略中心、数据库策略、真实数据或无法闭合的调用链 | 写明缺失证据、影响假设和最小验证方式 |
| 运行态已验证 | 仅在用户授权的非生产环境中通过权限矩阵或集成测试复现 | 记录环境、主体、资源、请求、预期与实际结果；不得把生产攻击作为默认步骤 |

“未发现问题”不等于“系统安全”。Security 专项必须在报告中披露已覆盖的入口、受保护动作、授权机制和未覆盖的外部证据。

### 越权问题最小证据字段

- 入口与位置
- 主体及身份来源
- 受保护动作
- 资源及资源标识来源
- 授权证据与决策点
- owner/tenant/org/role/scope 绑定结果
- 未授权路径与最终敏感效果
- 已存在的有效防护及其限制
- 置信度与证据状态
- 待确认项的最小验证用例

## 6. 安全问题分级

沿用全局 P0 五项硬门槛：生产可达、证据完整且置信度高、事故级影响、缺少有效防护、必须阻断发布。网络位置、匿名/已认证和利用前置条件只能作为证据，不能单独决定级别。

认证/鉴权/安全开关判定路径上的 fail-open（异常、空值、未处理路径默认放行）按认证绕过候选定级：代码链闭合只能证明静态触发路径和缺少拒绝分支；只有入口注册、装配以及部署/运行配置也由仓库证据闭合时，才满足“生产可达”。否则归入待确认并显式标注“P0 待验证”；依赖异常、配置缺失等常规运维事件不应被当作低概率理由，但仍需补齐外部可达性证据。

- 证据完整、影响达到事故级且无有效防护：P0。
- 证据成立但影响较小，或有显著缓解措施：P1。
- 局部风险、加固建议或缺少完整影响链：P2/P3。
- 怀疑高危但缺生产可达性、调用链、运行配置或防护状态：待确认，并标注“P0 待验证”（如适用）。
- 仅缺少注解、命名不规范或“建议统一鉴权”而没有未授权可达路径，不得直接定为越权漏洞。

## 7. 验证方案契约

当静态证据不完整或需要回归验证时，生成最小、非破坏性的权限矩阵用例，不自动对生产系统发起攻击：

| 主体 | 资源 | 动作 | 预期 |
|------|------|------|------|
| 用户 A | A 的资源 | 查看/修改 | 允许 |
| 用户 B（同角色） | A 的资源 | 查看/修改 | 拒绝 |
| 普通用户 | 管理资源 | 管理动作 | 拒绝 |
| 租户 B | 租户 A 资源 | 查询/导出/下载 | 拒绝 |
| 无身份/过期身份 | 受保护资源 | 敏感动作 | 拒绝 |

验证方案必须指定：测试环境、凭据来源、资源种子、请求位置、预期状态码/业务结果、是否只读、清理与回滚方式。没有用户授权、测试环境或凭据时只输出方案，不执行验证。

## 8. Security 专项覆盖清单

结束前必须确认并披露：

- 入口类型与数量是否完成覆盖。
- 认证、授权、租户隔离和主体传播是否完成取证。
- 高价值读/写/删/导出/下载路径是否完成主体—资源绑定检查。
- 异步、RPC、消息、回调、缓存和批量入口是否检查。
- 注入、外部资源、文件、敏感数据、业务重放和配置依赖是否检查。
- 每个安全契约是否记录默认行为、反例结果和外部待验证项。

安全专项的最终输出应让审阅者能够区分：代码已经证明什么、代码没有证明什么、下一步应如何安全验证。
