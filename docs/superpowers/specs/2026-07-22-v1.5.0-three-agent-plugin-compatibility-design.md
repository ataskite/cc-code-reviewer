# v1.5.0 Claude Code / Codex / ZCode 插件兼容设计

> 日期: 2026-07-22
> 状态: 设计待评审
> 目标版本: 1.5.0
> 关联计划: `docs/superpowers/plans/2026-07-22-v1.5.0-three-agent-plugin-compatibility.md`

## 一、背景与问题

cc-code-reviewer 当前是 Claude Code 原生插件：使用 `.claude-plugin` 分发，以 `skills/*/SKILL.md` 作为入口，通过 Claude 专属的 `AskUserQuestion`、插件 Agent 类型、`${CLAUDE_PLUGIN_ROOT}` 和 Claude 模型名称完成 scan、ignore、fix。

项目的审查内核本身并不依赖 Claude：

- `scripts/core/`、`scripts/languages/*/` 是 Bash + perl 的确定性执行层。
- `references/` 保存语言规则、报告格式、ignore/fix 契约。
- `agents/*.md` 的主体是审查角色、输入边界和输出要求。
- 批次计划、状态文件、结果文件和合并报告都是文件协议。

真正的平台绑定集中在四处：

1. **分发绑定**：只有 `.claude-plugin/plugin.json` 和 Claude Marketplace 清单。
2. **入口绑定**：Skill 使用 `${CLAUDE_PLUGIN_ROOT}`，frontmatter 缺少 Codex/ZCode 要求的稳定 `name`。
3. **交互绑定**：人工确认状态机被写成 `AskUserQuestion` 的具体参数，而不是平台无关的确认语义。
4. **调度绑定**：Skill 直接指定 Claude `subagent_type`、`model: sonnet/opus/haiku`，Agent frontmatter 也绑定 Claude 模型。

因此，1.5.0 的任务不是重写代码审查器，而是给同一套审查产品增加三个确定性的宿主适配器。

## 二、目标

1. 同一 Git 仓库、同一版本号可被 Claude Code、Codex CLI/Desktop、ZCode 安装。
2. 三个平台都提供 scan、ignore、fix 三个入口。
3. 三个平台共享同一套流程、脚本、规则、Agent Prompt 主体和报告契约。
4. 保持现有核心不变量：预扫描先行、摘要先于交互、逐步确认、范围确认后执行、子 Agent 不上传飞书、批次结果由主入口合并。
5. 平台不具备某项可选能力时显式降级，不静默改变审查范围或并发计划。
6. 所有分发清单的版本、名称、Skill 集合由自动化测试阻止漂移。

## 三、非目标

- 不修改 Java/前端/Python 的审查维度与严重级别。
- 不修改固定 1M 上下文分批、First-Fit Decreasing、Maven 模块规划和合并算法。
- 不为三个平台复制三套完整 Skill。
- 不在 1.5.0 引入新的 MCP Server、Hook 或 LSP 插件依赖。
- 不把 Codex IDE Extension 纳入插件安装承诺；当前以 Codex CLI/Desktop 为正式支持面。
- 不把进入 OpenAI 公共插件目录或 ZCode 官方市场作为发版门禁。
- 不支持 Windows。

## 四、平台能力基线

| 能力 | Claude Code | Codex | ZCode |
|---|---|---|---|
| 原生插件清单 | `.claude-plugin/plugin.json` | `.codex-plugin/plugin.json` | `.zcode-plugin/plugin.json` |
| Git Marketplace | 已支持 | `.agents/plugins/marketplace.json` | 自定义 GitHub/Git source |
| Skill | `SKILL.md` | `SKILL.md` | `SKILL.md` |
| 原生插件 Agent | 已支持 | 插件清单不作为主要分发面 | 已支持，Beta |
| 通用 subagent | 已支持 | 已支持 | 已支持/可由原生 Agent 承担 |
| 结构化提问 | `AskUserQuestion` | 能力存在时使用；选项/多选受限 | 能力存在时使用 |
| 当前约束 | 现有主平台 | 插件主要面向 CLI/Desktop | 插件体系仍为 Beta |

设计只依赖各平台公开、可验证的插件/Skill 能力。ZCode 当前能够兼容读取 Claude/Codex 清单是加分项，但不作为架构依赖。

## 五、核心设计决策

### 5.1 一套产品内核，三端原生清单共同发现

不采用“共享 Skill 运行后再猜宿主平台”的方案。平台检测如果依赖已安装目录、工具名称或不稳定环境变量，会在同时安装多个 Agent 产品时产生歧义。

Codex 官方 ingestion validator 要求 `plugin.json.skills` 解析到根 `skills/`。因此 1.5.0 采用三端共同发现同一组根 Skill，而不是 Codex 自定义 Skill 路径：

```text
runtime/
  contract.md                         # 所有宿主必须实现的能力接口
  claude-code.md                      # Claude 工具映射
  codex.md                            # Codex 工具映射
  zcode.md                            # ZCode 工具映射

skills/                               # 三端共同发现的唯一权威流程
  cc-code-reviewer/SKILL.md
  cc-code-ignore/SKILL.md
  cc-code-fixer/SKILL.md

```

每个共享 Skill 在预扫描前只执行以下 bootstrap：

1. 声明标准 `name` 和 `description`。
2. 从当前宿主身份固定 `RUNTIME_ID=claude-code|codex|zcode`；身份不明确时失败，不根据文件或工具猜测。
3. 加载对应 `runtime/<platform>.md`。
4. 继续执行当前唯一权威 Skill。

三端差异不得进入状态机、脚本列表、参数表、Agent Prompt 或报告规则。

### 5.2 Claude 调用名保持兼容

现有 Claude 用户的以下入口不能失效：

```text
/cc-code-reviewer:cc-code-reviewer
/cc-code-reviewer:cc-code-ignore
/cc-code-reviewer:cc-code-fixer
```

因此根目录 `skills/` 同时由 Claude、Codex、ZCode 原生清单发现，既不复制业务正文，也不破坏 Claude 的现有调用名。

Codex 和 ZCode 清单分别指向各自的 `platforms/*/skills/`，从安装阶段确定宿主身份。

### 5.3 共享 Skill 是执行契约单一真相源

三个完整 `SKILL.md` 保持唯一业务正文。

权威 Skill 只使用逻辑动作，不出现平台工具名：

- `INTERACT`
- `DISPATCH_AGENT`
- `PLUGIN_ROOT`
- `MODEL_PROFILE`

每个逻辑动作必须在三个 runtime adapter 中有明确映射。缺少映射时在执行预扫描前失败，不能运行到一半再发现平台不支持。该布局是基于官方 Codex validator 对初版“九个薄入口”的实现期修正。

## 六、运行时接口

### 6.1 运行时上下文

共享 Skill 进入业务状态机前必须提供：

| 字段 | 含义 | 约束 |
|---|---|---|
| `RUNTIME_ID` | `claude-code` / `codex` / `zcode` | 由当前宿主身份固定，不按工具或目录猜测 |
| `PLUGIN_ROOT` | 当前插件实际根目录 | 必须为绝对、可读路径 |
| `INTERACTION_MODE` | `structured` / `sequential-text` | 在首次交互前确定 |
| `AGENT_DISPATCH_MODE` | `native-agent` / `generic-subagent` | 在最终确认前展示 |
| `MODEL_PROFILE` | `inherit` / `economy` / `balanced` / `maximum` | 默认 `inherit` |
| `OPTIONAL_CAPABILITIES` | lark、Superpowers 等 | 缺失只能影响对应可选路径 |

### 6.2 插件根目录解析

`PLUGIN_ROOT` 是逻辑变量，不要求三个平台暴露同名环境变量：

- 三端都从当前被加载的根 `skills/<skill>/SKILL.md` 资源位置向上两级解析插件根目录。
- 解析完成后，共享 Skill、scripts 和 Agent Prompt 只使用 `${PLUGIN_ROOT}`。
- 不使用当前工作目录推断插件根目录。
- 解析必须支持路径空格、Marketplace cache、符号链接；失败时不得继续预扫描。

### 6.3 交互接口

共享 Skill 规定的是状态机，不是某个工具调用：

```text
preflight
  -> preflight_summary
  -> review_mode
  -> model_profile
  -> report_targets
  -> review_entry
  -> review_scope
  -> optional_batch_strategy
  -> optional_batch_count
  -> optional_concurrency
  -> final_confirmation
  -> execution
```

必须保持：

- `preflight` 完成前不提问。
- `preflight_summary` 只输出一次，且必须在第一个问题之前。
- 每个状态等待用户响应后才能进入下一状态。
- 不允许通过用户输入中的命令行式参数绕过状态。
- `final_confirmation` 必须独立存在。
- fix 只执行确认后的问题集合。

平台映射：

- Claude：继续严格使用 `AskUserQuestion`；现有 multiSelect 规则保留。
- Codex：有结构化输入能力时使用；若一次只能提供 2–3 个选项，将 4 个以上选项拆成分级菜单；无多选时把多选转换为连续的是/否选择或预定义组合。
- ZCode：优先使用原生结构化输入；缺少对应能力时与 Codex 使用相同的逐轮降级。
- 只有宿主没有结构化输入能力时，才允许 `sequential-text`；一次只问一个问题，必须等待响应，不得把多个步骤合并成一段文本。

这意味着跨平台最高优先级契约从“必须调用名为 AskUserQuestion 的工具”调整为“必须执行等价的逐步人工确认状态机”；Claude 适配器仍保持原工具约束。

### 6.4 模型接口

`REVIEW_MODE` 与 `MODEL_PROFILE` 分离：

- `REVIEW_MODE=fast|standard|deep|security` 决定审查维度和输出门槛，保持现状。
- `MODEL_PROFILE=inherit|economy|balanced|maximum` 只决定宿主模型/推理强度。

默认 `inherit`，避免把随平台版本变化的模型 ID 写进共享 Skill。具体模型映射只存在于 runtime adapter，并允许随平台版本更新而不改审查契约。

fast 模式“仅输出 P0”的现有语义不因模型档位改变。

### 6.5 Agent 调度接口

共享 Agent 文件保留统一的角色、参数表、范围和输出正文，平台 frontmatter 降到最小：

- 移除强制 `model: sonnet`，默认继承主入口选择的模型档位。
- Claude：通过现有插件 Agent 类型调用。
- Codex：主 Skill 读取对应 `agents/*.md` 正文，注入参数后派发通用 subagent。
- ZCode：读取同一 `agents/*.md` 正文并使用通用 subagent + Prompt 注入；1.5.0 不声明官方文档未确认的 manifest agent 字段。

`DISPATCH_AGENT` 输入必须统一：

| 字段 | 必须性 |
|---|---|
| 项目、语言、审查类型、审查范围 | 必须 |
| 预扫描结果、ignore 规则 | 必须 |
| Agent Prompt 路径、review framework 路径 | 必须 |
| source manifest 或 batch scan roots | 按模式必须 |
| batch plan/status/result 路径 | batch 必须 |
| semantic level | 必须 |
| model profile | 必须 |

子 Agent 不与用户交互、不上传飞书、不扩展正式扫描范围。平台没有可用 subagent 时，scan 在最终确认前报告阻塞；不得让主 Skill 静默接管实际审查，从而破坏现有职责边界。

## 七、分发设计

### 7.1 清单

```text
.claude-plugin/plugin.json
.claude-plugin/marketplace.json
.codex-plugin/plugin.json
.agents/plugins/marketplace.json
.zcode-plugin/plugin.json
VERSION
```

`VERSION` 是版本单一真相源，内容为 `1.5.0`。各平台 schema 仍需重复版本字段，因此测试必须校验所有字段与 `VERSION` 完全一致。

三个插件清单必须共享：

- `name=cc-code-reviewer`
- repository、license、author
- scan/ignore/fix 三个逻辑能力
- 同一版本号

各自只在 schema、Skill 路径、Agent 注册和 Marketplace policy 上不同。

### 7.2 分发路径

- Claude Code：继续通过现有 GitHub Marketplace 安装。
- Codex：通过 `codex plugin marketplace add owner/repo` 添加 Git Marketplace，再安装插件。
- ZCode：通过 Settings → Plugins → Marketplace 添加同一 GitHub/Git source。

1.5.0 不要求构建三份 ZIP。Git 仓库就是统一分发物；平台只读取各自清单和入口目录。

### 7.3 信任面

1.5.0 不新增 hooks、MCP server 或自动执行安装脚本，降低三个平台首次安装时的信任提示和安全面。现有脚本只在用户确认的审查/fix 流程中执行。

## 八、兼容与迁移

### 8.1 保持不变

- Claude 插件名称、Marketplace 名称和三个调用名。
- `.cc-code-reviewer/` 项目文件协议。
- ignore 文件格式。
- 批次 plan/status/result/summary 格式。
- 报告 Markdown、飞书 Doc/Base 字段。
- Java、前端、Python 语言路由和正式源码边界。

### 8.2 有意变化

- 根 `SKILL.md` 保持完整且平台中立，三端原生清单共同发现。
- `${CLAUDE_PLUGIN_ROOT}` 从共享业务流程移除。
- 模型选项从 Claude 产品名变为平台无关档位。
- 跨平台人工确认契约不再绑定某一个工具名；Claude 行为保持不变。
- Agent Prompt 不再强制 `sonnet`。

### 8.3 迁移顺序

1. 先用测试锁定现有 Claude 行为。
2. 将根 Skill 的交互、模型和调度动作平台中立化，证明 Claude 无回归。
3. 增加 Codex 原生清单并通过官方 ingestion validator。
4. 增加 ZCode 原生清单，跑通同一 smoke matrix。
5. 最后切换版本同步、README 和发版说明。

任何阶段 Claude 回归测试失败都停止扩展下一平台。

## 九、失败与降级语义

| 场景 | 行为 |
|---|---|
| 插件根目录无法解析 | 预扫描前失败，给出宿主与 Skill 路径 |
| 宿主没有结构化提问工具 | 逐轮单问降级，不能跳步 |
| 宿主没有 subagent | 最终确认前阻塞，不由主 Skill 接管审查 |
| 并发能力不足 | 展示实际并发数，用户重新确认后串行/低并发执行 |
| lark-cli 不可用 | 仅禁用飞书输出，本地报告继续 |
| Superpowers 不可用 | fix 只展示直接修复路线 |
| ZCode 原生 Agent 清单不兼容 | 降级为通用 subagent + Prompt 注入 |
| 某平台清单版本漂移 | 自动化测试失败，禁止发布 |

降级不得改变正式扫描文件集合、问题严重级别或修复范围。

## 十、测试与验收设计

### 10.1 静态契约测试

- 所有清单 JSON 可解析、必填字段存在、版本等于 `VERSION`。
- 每个平台恰好暴露三个 Skill，Skill `name` 唯一且稳定。
- 三端原生清单必须指向同一组根 `skills/`。
- 共享 Skill 必须引用 runtime contract，并只使用 `INTERACT`、`DISPATCH_AGENT`、`MODEL_PROFILE` 等逻辑能力。
- 共享 Skill 不得出现 `${CLAUDE_PLUGIN_ROOT}`、Claude `subagent_type` 或具体模型 ID。
- runtime adapter 必须完整实现运行时接口表。

### 10.2 Claude 回归测试

- 三个旧调用名仍可发现。
- 预扫描、摘要、逐步提问顺序不变。
- 单 Agent、batch、ignore、fix 和飞书职责边界不变。

### 10.3 三端 smoke matrix

每个平台在干净安装环境至少验证：

1. 安装并在新会话发现三个 Skill。
2. Java 小项目单 Agent scan。
3. 前端或 Python file-token batch scan 和报告合并。
4. 从报告执行一个确认后的 fix。
5. 写入一条 ignore 并验证下一次 scan 过滤。
6. 无 lark-cli 时生成本地报告。

核心流程任一失败均阻塞 1.5.0。

## 十一、备选方案与取舍

### 方案 A：只增加 Codex/ZCode 清单，共享现有 SKILL.md

**不采用。** 安装可能成功，但 `${CLAUDE_PLUGIN_ROOT}`、`AskUserQuestion`、Claude Agent 类型和模型名会在运行期失败，只解决“可发现”，没有解决“可执行”。

### 方案 B：复制三套完整 Skill

**不采用。** 当前 scan Skill 很长且契约密集，三份副本会快速漂移，任何批次或语言变更都要同步三次。

### 方案 C：同一 Skill 按工具或目录自动猜测宿主

**不采用。** 同机同时安装 Claude、Codex、ZCode 时，按目录和工具存在性推断容易误判；平台工具和环境变量也可能随版本变化。

### 方案 D：三端原生清单 + 共享根 Skill

**采用。** 当前宿主身份直接选择 adapter，不按文件或工具猜测；三端清单共同发现官方 schema 支持的根 `skills/`，平台差异集中、可测试，业务流程只有一份。

## 十二、风险与控制

1. **Skill 未读取对应 adapter**：共享 Skill 明确要求预扫描前读取 runtime contract 和当前宿主 adapter；三端 smoke test 验证。
2. **Codex 结构化交互能力随模式变化**：规范逐轮单问降级，保留状态机而不依赖工具存在。
3. **ZCode Beta schema 变化**：原生清单单独验证；不让 ZCode 特有字段进入共享 Skill。
4. **现有未提交 Python/前端修改混入**：实施按文件窄暂存，基线任务先记录 diff；兼容提交不得顺带修语言逻辑。
5. **平台模型名称快速变化**：共享层只使用稳定档位，具体映射留在 adapter。
6. **平台中立化导致 Claude 行为回归**：保留 Claude adapter 对 `AskUserQuestion` 与插件 Agent 的原映射，并跑完整回归。

## 十三、完成判定

设计实现完成必须同时满足：

- 一份 workflow 驱动三个宿主，没有完整流程副本。
- 三个平台均能从同一 Git 仓库安装并发现三个 Skill。
- 三端 smoke matrix 全部通过。
- Claude 现有入口和执行语义无回归。
- 人工确认、子 Agent 边界、正式扫描范围、批次合并和飞书职责保持一致。
- 所有清单版本与 `VERSION=1.5.0` 一致。
